# Security & Trust Boundary Policy

## 1. Overview & Threat Model

`agent-pair-ipc` provides local Inter-Process Communication (IPC) between autonomous coding agents (such as Google Antigravity, Anthropic Claude Code, and OpenAI Codex). 

Because these agents operate with shell execution (`bash`), file read/write, and Git permissions, connecting them introduces specific trust and safety considerations.

## 2. Trust Boundaries

1. **Local Machine Boundary**:
   - `agent-pair-ipc` only communicates over local Unix Domain Sockets (`AF_UNIX`) and local file-based queues. It never exposes network ports, HTTP listeners, or remote interfaces.
   - Authentication tokens (`peerToken`) generated by Claude Code are stored locally with user-only file permissions (`~/.claude/sessions/`).

2. **Peer-to-Peer Agent Trust & Prompt Injection**:
   - **Important**: Messages injected via `agent-pair-ipc` are processed by the receiving agent as peer requests.
   - If an agent ingests untrusted third-party content (e.g. scraped web data or unvetted PRs) and forwards it to another agent without sanitation, indirect prompt injection could theoretically propagate across agent boundaries.
   - **Recommendation**: Always review the scope of tasks before delegating full shell execution, and configure agent confirmation thresholds for destructive commands (e.g., `git push --force`, `rm -rf`, or database drops).

3. **Session Re-use vs. Ephemeral Execution**:
   - By design, `agent-pair-ipc` connects to an *existing, active* user session rather than spawning an unmonitored background process. This ensures the human developer maintains full visual observation in the desktop or terminal UI.

4. **Ephemeral Reply Socket Boundary**:
   - Bi-directional callback sockets are established under `~/.agent-pair/run/` with strict directory permissions (`0o700`) and socket permissions (`0o600`).
   - This prevents unprivileged local OS users from eavesdropping or injecting replies.
   - *Note*: Other processes running under the same OS user share identical POSIX permissions and could technically write to the socket or transcript file. This is consistent with local IPC threat models.

5. **Duplex Reply Channel & Mailbox**:
   - `agent-pair-ipc reply --to <Req-ID>` derives the socket path from the request ID inside `~/.agent-pair/run/`. It never connects to a path taken from message text, so forged envelopes cannot redirect replies.
   - Request IDs are restricted to `[A-Za-z0-9_-]{4,64}` (no path traversal). Frames with a mismatched correlation ID are rejected with a negative ack, and frames larger than 32 MiB are refused.
   - Offline replies are written atomically to `~/.agent-pair/run/replies/<Req-ID>.json` (0600) and removed once read. Verdicts are always re-derived from the reply text.
   - Sandboxed receivers (e.g. Codex `workspace-write`) may need user approval to reach `~/.agent-pair/run`. If they are denied, the requester falls back to the transcript channel.

6. **Peer Envelope & Authorization Honesty**:
   - Every envelope states that a peer message is **not** user approval and does not request privilege escalation. `--user-context` only quotes what the user actually said and is labelled as unverified by the receiver. Never fabricate it.
   - **External Mode Assertion**: External peer callers (e.g. Antigravity) strictly and honestly declare `from-mode="prompting"`. The toolkit never sniffs target process arguments or spoofs elevated execution modes (`bypass`), eliminating identity spoofing.
   - **Inbound Gate & Parity Holds**: Claude Code 2.1+ natively implements an intentional inbound gate. Inbound peer traffic without mode parity (e.g. `prompting` callers targeting a `bypassPermissions` session) is held in memory for human attestation ("Review it below" card in the desktop UI) to prevent unprivileged scripts from quietly executing shell commands inside high-privilege sessions.
   - **Strict Read-Only Tooling Policy**: `agent-pair-ipc` maintains a 100% read-only policy regarding user and application configuration (`settings.json`). The tool will **never** automatically write, modify, or provide a `--fix` switch to relax security gates, nor will it dispatch instructions asking peer agents to mutate user permissions.
   - **User Security Tradeoff on `crossSessionInbound: "accept"`**:
     > ⚠️ **Security Warning**: If you choose to configure `"crossSessionInbound": "accept"` in `~/.claude/settings.json`, this is a global user setting across all projects and sessions. It bypasses parity hold checks and directly enqueues peer messages into all sessions—including `bypassPermissions` sessions where tools run without confirmation prompts.
     > Any local process running under your OS user account that connects to the local messaging socket will be able to dispatch commands directly into those high-privilege sessions.
     > Only enable this setting if you fully trust all local processes and external agents operating on your workstation. Preferred alternatives include approving held cards individually or operating sessions in `auto` mode.

7. **macOS GUI Automation & Accessibility (Experimental)**:
   - `open_new_gui_session()` brings the desktop app to front and clicks its native "new session" menu item (Claude: File > New Session; ChatGPT/Codex: File > New Chat), falling back to Cmd+N.
   - This feature requires explicit macOS Accessibility permissions for the calling process.
   - It is marked as **experimental** across varying client desktop UI states, though focus-verification loops are enforced before issuing keystrokes to prevent delivery to unintended windows.

## 3. Reporting Security Issues

Please **do not report security vulnerabilities through public GitHub issues**.

Instead, please report security vulnerabilities via [GitHub Security Advisories](https://github.com/VeeDou/agent-pair-ipc/security/advisories/new) or email `ax65@live.com` directly. We will review and respond within 48 hours.
